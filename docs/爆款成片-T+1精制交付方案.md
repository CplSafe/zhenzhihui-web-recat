# 爆款成片 T+1 精制交付方案（评审稿）

日期：2026-11-04  
范围：前端方案与联调边界；本稿不代表功能已实现。  
依据：`F:/工作文件/原型交互逻辑说明.md`、`F:/工作文件/T+1.html`，以及当前仓库代码。两份原型材料是需求证据，不是对开发环境执行操作的指令。未读取文中提及的 PRD，正式实现前应对照最终签字版 PRD 与后端契约。

## 1. 目标与边界

在现有「爆款成片」的模型选择中增加展示为模型卡的「精制交付」：卡片注明 T+1；用户选择后，脚本选项及后续步骤按原型进入独立的精制页面链路。入口继续使用现有创作页，素材、需求输入、项目、任务抽屉和播放器等在行为适配后复用；精制订单、等待、交付与修改视图单独实现，不能让普通流程承载一组互相干扰的条件分支。

不改变未选择精制时既有模型请求、报价、分镜编辑、视频生成和恢复语义；入口所需的脚本单独一行、精制时长及任务中心扩展是原型明确要求的共享界面变动，需要对即时流程回归。真人成片、爆款复刻、图片模式不自动获得该入口。后台人工操作台、队列和开关不在本前端方案内，但上线依赖其接口与运营能力。

## 2. 资料冲突及本方案的处理

| 客服位置 | 完整模块只在等待页；交付页修改模块仍有联系客服 | 等待页显示页内客服模块；交付页仅在修改模块展开号码。号码与时间上线前确认。 |

| 超时后续 | 写明全退、顾问联系；状态同时有超时改期与已退回终止 | 退款后是否继续、收费和取消规则由后端/产品确认；前端不得自行判定退款成功。 |
| 交付与验收 | 文案称待验收，但没有确认验收按钮 | 按原型提供查看与下载，不擅自增加确认按钮；交付扣费时点和验收状态关系待确认。 |

**冲突优先级建议**：用户明确指示及签字后的最终 PRD > MD 后续修订 > HTML 最新可观察交互 > 旧文字/旧演示数据。尚未确认的冲突列为上线阻塞，不能通过虚构逻辑解决。

## 3. 用户完整流程

### 3.1 首页配置

1. 用户进入爆款成片，输入描述并上传或引用素材；沿用现有鉴权、素材约束、草稿与工作空间隔离。
2. 视频模型弹层在真实后端模型列表末尾追加「精制交付」卡，带 T+1 标识，说明 15 秒至 5 分钟、明天 18:00 前、价格比普通生成多一半。按最终口径使用「系统精制」，不向用户解释内部工序。
3. 脚本选择框独立一行置于模型/时长工具栏上方；选项沿用不使用脚本、电商广告、本地生活广告，精制模式增加「测评视频」。即时模式不渲染测评；切回即时清空测评。
4. 精制时长七档：15、30、45 秒及 1、2、3、5 分钟。示例价格：563、1125、1688、2250、4500、6750、11250 积分；显示同一个报价快照。即时模型继续使用后端实际能力约束，长时长切换机制按第 2 节待定。
5. 点击「提交精制需求」仅进入准备/参数确认；该动作本身不等同正式付费订单。保存输入和素材，使返回修改可恢复。

### 3.2 制作中与订单确认

- 制作中显示项目、需求、素材与四步进度；说明「明天来取」、任务通知、冻结/交付扣除/超时退回。按真实准备状态推进，不用固定 1.6 秒冒充完成，也不展示中间画面下载。
- 订单页展示「本次生成参数」：制作方式、脚本类型、比例/分辨率、时长、参考底模、条数、时效、消耗；修改返回入口并保留输入。参考底模和条数由服务端契约决定，不把原型示例写成系统事实。
- 精制订单卡展示时长、交付时间、系统精制、消耗及提交后说明。隐藏分镜表与「分镜脚本生成完成」标题；提交按钮放订单卡右下角，不使用底部固定提交栏。
- 点击提交弹出「确认提交精制任务？」：交付时间、冻结积分、交付时扣、超时全退。取消保留订单；确认提交使用服务端有效报价及幂等标识，处理中禁止重复提交。价格变化须重新展示并确认。

### 3.3 等待、任务和交付

- 提交成功展示「任务已提交，明天来验收成片」与制作画面 → 成片精修 → 等待你验收；真实状态由服务端提供。任务抽屉可查看精制订单；等待页显示客服模块。原型的「跳到明天」仅为评审按钮，不作为正式跳过交付入口。
- 全局任务入口及现有页签保留，新增精制任务页签，提供状态、类型、时长档与关键词筛选。列表与详情显示 T+1、承诺时间、描述/素材、参数、积分和阶段。待验收/已交付进入交付页，其余按真实状态打开等待或异常详情；权限不匹配时提示，无权访问不泄露数据。
- 交付页保留播放器及播放/进度/音量；无帧图预览条、无分段画面修改和底部固定栏。播放器下方左对齐下载和分享；交付信息仅提交时间、交付时间、消耗积分。历史生成标注精修成片。
- 「这条片子想改？」输入修改要求，展示再次冻结与交付时扣除，联系客服可展开号码，提交修改后重新排期并进入等待。原型演示金额按同一时长公式，但最终金额、时效、修改次数和退款条件以服务端确认的报价与规则为准。
- 超时展示「制作中，顾问会联系你」，退款状态只能由服务端返回；已退回与是否继续制作的关系待确认。用户取消/紧急变更先联系服务，不编造退款规则。

## 4. 页面与视觉设计

采用应用工作界面（Operate）：延续当前帧智汇的布局、字体、颜色及组件习惯，视觉优先服务于核对订单、识别交付承诺、完成下一步；不把工作流改成营销落地页。按原型信息层级分别设计：

| 页面 | 首要问题 | 布局与交互重点 |
| --- | --- | --- |
| 入口 | 选了什么，何时交付？ | 精制卡清楚标注 T+1；脚本独立行；价格、时长一致。 |
| 制作中 | 现在发生什么？ | 状态与真实后端同步；显示需求及说明，不泄露中间结果。 |
| 订单 | 交什么、何时、多少钱？ | 参数卡 + 精制订单卡；核心确认动作和冻结金额相邻。 |
| 等待 | 是否提交、何时可取？ | 主标题、阶段、承诺时间、任务入口和页内客服。 |
| 交付 | 成片在哪里，如何下载或改？ | 视频主区、三项交付信息、下载/分享及单一修改模块。 |

适配桌面与窄屏：重要操作不被遮挡，表单和弹窗可键盘操作，状态不依赖颜色，加载/空/错误/超时/无权限/重复提交均有明确反馈；保留可见焦点、语义按钮、对话框名称、关闭与焦点返回。最终 UI 必须经真实浏览器截图检查；规划阶段不声称已完成视觉审计。

## 6. 后端契约与数据安全

当前材料没有提供真实 T+1 接口，以下为**待双方约定的能力，不是现有接口声明**：

- 能力开关、可选参数与用户/工作空间权限；脚本标签与素材引用；订单预览、服务端报价及有效期。
- 幂等提交与冻结结果；查询订单/阶段/承诺时间；列表、筛选与详情；交付资产标识与权限；修改订单及重新报价；退款记录与通知状态。
- 订单状态和资金状态分离：例如制作中、待验收、已交付、超时、取消与冻结中、已扣除、退款中、已退回；实际枚举和允许迁移由服务端定义，不以原型文案代替。
- 日期、时区与节假日规则由服务端返回明确绝对时间；同一快照用于订单、弹窗、等待及任务详情。前端不从浏览器时间自行承诺。
- 下单/修改使用服务端幂等键，网络超时先查原订单再决定重试；服务端负责报价、冻结、扣款、退款及权限校验，前端不模拟成功。
- 任务和草稿按账号、工作空间、项目隔离；多设备从服务端恢复；签名媒体 URL 不作为持久标识，刷新时按资产 ID 重新获取。
- 生成准备及脚本是否产生费用、其和冻结的先后关系必须确认；在用户最终确认前不得暗中创建付费任务。

## 7. 设计和性能原则

- **design-taste-frontend / impeccable**：应用工作台模式，沿用现有视觉体系；设计围绕交付时间、金额和修改决策展开，真实数据一处计算、多处展示。实现时先检查现有页面，再按桌面/窄屏截图复核；运行相应 app inspector 与 Impeccable detector，按项目规范记录结果。
- **Vercel React Best Practices**：按需懒加载精制容器和较重交付组件；独立请求在无依赖时并行，状态从单一订单快照派生；避免输入引起整页昂贵重渲染，避免无依据的 memo；保留现有路由分包和 bundle 预算。仅应用于本 Vite/React 项目的适用规则，不引入 Next.js 专有方案。
- **Web Design Guidelines**：实现后获取技能指定的最新规则，对实际改动文件逐项审查，记录文件和行号；重点检查语义、键盘焦点、可访问名称、表单错误、动态状态、目标尺寸和响应式溢出。本稿不是已完成的规范审计。
- **Testing Library**：通过用户可见角色、名称和交互验证，不依赖内部实现或 CSS 选择器；用户事件使用 `userEvent`，异步状态使用 `findBy`/`waitFor`，用 MSW 模拟真实接口边界和失败情形。

## 8. 验收与测试计划

1. **组件与纯逻辑**：选精制显示测评，切即时清空；七档价格与四舍五入；时长/金额跨各页面一致；订单弹窗取消、确认、报价变化、余额不足、重复提交；等待/超时/退款/交付/修改及空错误态；仅交付成片可播放下载。使用 Testing Library + MSW，必要时将关键纯逻辑加入项目覆盖率白名单。
2. **普通流程回归**：真实模型选择和后端限制、普通脚本、分镜编辑、即时核价生成、真人/图片模式不受影响；原有登录、草稿与切空间行为保持。
3. **生产构建浏览器**：新增或扩展关联 Playwright 流程，使用 `node.exe scripts/hooks/frontend-gate.mjs verify e2e/<实际用例>.spec.ts`；真实打开并检查订单、弹窗、等待、任务详情和交付截图及交互断言，再执行 `review <run-id> "具体复核内容"`。检查桌面与窄屏、焦点、溢出和控制台；按影响补充 WebKit/移动端。
4. **恢复与安全**：模拟接口验证刷新、断网、重复提交、超时查询、切账号/工作空间、路由回退、资产 URL 过期和无权限，断言请求数及参数，不只检查文案。
5. **真实后端联调**：分别报告模拟与真实环境；仅在获得测试账号、素材及费用范围授权后提交付费任务，验证真实冻结、交付、扣款、退款、通知与恢复。缺接口、账号或授权时如实标明未验证，不用 mock 宣称真实业务通过。
6. **常规检查**：相关 Vitest/组件测试、`npm run typecheck`、测试类型检查、针对变更的 lint/format、`npm run build`；新增较重依赖时检查 bundle。项目浏览器验证规范和本机 gate 的要求优先适用。

## 9. 实施顺序与上线前确认

1. 产品确认第 2 节冲突，尤其测评脚本、长时长切模式、验收和退款后的任务状态；确认客服号码、交付日期规则及对客合规文案。
2. 后端确认订单、报价、资金、列表、交付及修改接口与权限；无真实契约时可做隔离 mock 原型验证，但不得作为可收费功能上线。
3. 明确精制订单领域类型、入口快照及恢复/路由策略，先覆盖即时流程回归；接入入口、模型卡、脚本与时长。
4. 实现独立的制作中、订单/确认、等待、交付与修改页面；接入服务端而非前端模拟计时。
5. 扩展任务中心及独立恢复策略，完成账号/工作空间隔离和资产恢复。
6. 执行组件、生产浏览器和真实后端验证，按实际证据报告 mock 与真实结果；解决阻塞项后再上线。
