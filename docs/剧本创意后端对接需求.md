# 剧本创意后端对接需求

> 文档日期：2026-11-05。根据当前前端代码和原型整理，供前后端及产品确认。本文标记为“建议”的字段名、路径和枚举均为待协商方案，并非声明现有后端已经实现。

## 1. 对接目标与现状

“剧本创意”包含创作者入驻、创意提交、一卡、剧本、完善剧本、审核和进度查询。每条创意对应独立流程；创作者入驻是账号资料，不创建创意任务。

当前真实申请接口仅支持首次提交姓名、电话、学校和一段创意正文；后续阶段只提交一段正文。剧名等信息被拼接进正文，无法可靠地按独立字段查询。创作者入驻资料保存在浏览器本地；四阶段完整表单和审核动作是本机演示；附件未上传。需要后端支持结构化字段、附件、四阶段流程及列表查询，前端也需配合改造。

## 2. 通用约定（建议）

- 认证：沿用当前登录态，服务端按登录账号隔离创作者资料与申请；申请 ID、任务 ID 需要进行归属及权限校验。
- JSON：除文件传输外使用 JSON。建议沿用现有响应外层 `{ "code": 0, "message": "", "data": {} }`；失败时返回可展示的错误信息和合适的 HTTP 状态码。
- 时间：统一约定 ISO 8601 时间字符串及含时区语义；现有接口的时间字段允许数字或字符串，兼容方案需确认。
- 写操作：首次提交和阶段提交保留 `X-Idempotency-Key`。同一账号、同一操作、同一 key 和相同请求体重试应返回原结果；同一 key 对不同内容应明确冲突。key 有效期和作用范围由后端确认。提交结果不确定时前端会使用原 key 和原请求体重试。
- 校验：后端独立校验必填、长度、数值、文件类型和大小；字段长度、数值上限及错误码由双方确认。前端目前以 Unicode 字符数校验真实提交：姓名最多 80、学校最多 200、拼接后的创意正文最多 12000、后续正文最多 20000；电话匹配 `^[\d+()\s-]{7,25}$`。这些是现有实现限制，并非结构化新接口最终规则。
- 历史：每次提交形成不可覆盖的版本快照，包括字段、附件引用、提交人和时间；审核意见关联对应版本。申请人信息建议提交时保存快照，避免资料修改改变历史记录。

## 3. 创作者入驻资料

按当前登录账号查询、创建和修改。建议提供 `GET /api/v1/script-creators/me`、`PUT /api/v1/script-creators/me`；路径待确认。资料未创建时应约定明确的空状态响应。

| 身份类型 | `identity_type` | string | 是 | 在校学生、自然流创作者、团队编剧、自由职业；编码待确认 |
| 学校 / 机构 | `school` | string | 是 | |
| 年级 / 专业 | `grade_major` | string | 否 | |

账号由登录态确定，无需提供可编辑的账号 ID。当前同意状态只在页面校验，没有作为资料字段持久化。

## 5. 附件能力

原型限制：每阶段最多 30 个文件，每个最大 500 MB，支持 `doc`、`docx`、`pdf`、`txt`、`md`、`ppt`、`pptx`。请确认数量是否按单阶段、单次提交或整个申请计算；按阶段保存及历史版本引用的具体规则也需确认。

需要提供上传、获取下载方式和提交时关联文件的能力。建议附件引用包含 `file_id`、`file_name`、`file_size`、文件类型；若下载地址有有效期，应支持按 `file_id` 重新获取。提交接口校验文件归属、上传完成状态、格式和大小，历史版本保留对应附件引用。上传协议、失败重试及大文件分片方式待后端确定。

## 6. 接口能力清单（建议，不是现有契约）

| 能力 | 建议接口 | 主要内容 |

| 创建并提交创意 | `POST /api/v1/script-applications` | 申请人快照、创意阶段字段、附件；返回申请 ID 和流程状态 |

| 申请详情 | `GET /api/v1/script-applications/{id}` | 申请信息、当前阶段及状态、当前待办、历史版本、审核记录和附件 |

### 列表查询与返回

建议支持按剧名、申请编号、申请人搜索，按阶段、审核状态、题材筛选，支持分页及总数。每条返回至少包括：申请 ID、剧名、题材、申请人、当前阶段、审核状态、创建时间、最近更新时间。请确认搜索匹配规则、排序方式及统计是否跟随筛选条件。

### 流程与审核

目标流程为创意 → 一卡 → 剧本 → 完善剧本。需要明确待提交、审核中、需修改、已撤回、已通过、已终止等业务状态及允许的动作。审核中只读，可撤回；退回后可按意见修改重提；阶段通过后进入下一阶段；终稿通过后全流程完成。具体状态码、撤回后流转、审核不通过与退回的区别，以及服务端自动推进规则待确认。

详情需返回当前任务 ID、阶段、状态、每次提交的版本号、字段和附件、提交时间，以及审核节点、结果、意见、关联版本和审核时间。权限不足、任务变化、重复提交或版本冲突时应返回明确错误；冲突后前端刷新详情并保留用户输入。

## 7. 现有前端接口与兼容性

以下是当前前端客户端调用，不代表对线上服务实际能力的验证。前端使用 `credentials: include`，读取响应的 `code`、`message`、`data`。

| 当前接口 | 当前前端契约 |
| --- | --- |
| `POST /api/v1/student-applications` | 请求 `name`、`phone`、`school`、`creative`；返回申请，前端使用 `id` |
| `GET /api/v1/student-applications?limit=20&offset=...` | 返回 `items`、`total` |
| `GET /api/v1/student-applications/{id}` | 返回 `application`、`progress_available`、`workflow`；后者包含状态、阶段、当前任务、版本及审核记录 |
| `POST /api/v1/student-applications/{id}/stages` | 请求 `task_id`、`stage`、`content`；返回提交版本 |

两个 POST 均携带 `X-Idempotency-Key`。首次提交时 `creative` 拼接了剧名、题材、故事正文及可选的第一集剧情、人物信息；后续阶段仅传 `content`。现有前端使用的阶段代码为 `creative`、`draft`、`revision`，与目标四阶段并非天然一一对应。

请后端确认是扩展现有接口还是新增版本化接口，并提供旧数据展示、阶段映射、灰度和回滚方案。历史自由文本不能保证准确拆分为结构化字段，建议保留原文；如何迁移及处理无法解析的数据需要明确。

## 8. 需要产品及后端确认

1. 四阶段编码、现有三阶段映射、审核状态及流转规则；不通过、退回、撤回和终止的区别。
2. 入驻资料与历史申请快照的关系；协议和原创声明是否记录版本、时间。
3. “重点付费 / 追更节点”的确切含义；题材及身份是否采用统一枚举，擅长题材是否为数组。
4. 各字段长度、数值范围、附件数量统计范围、文件上传及下载方案。
5. 列表统计口径、搜索和筛选规则、排序，以及审核记录、历史版本的返回范围。
6. 接口路径、请求响应示例、错误码、幂等有效期和旧数据兼容方案。

## 创作者入驻字段调整（待后端确认）

本节是前端拟定的对接需求，**不代表后端已支持**。页面将“学生状态”和“创作身份”拆开：

| 建议字段 | 类型与取值 | 规则 |
| --- | --- | --- |
| `student_status` | `student`（在校学生）或 `graduated`（已毕业） | 必填，独立保存与回显 |
| `creator_type` | `creator`（自然流创作者）、`team`（团队编剧）、`freelancer`（自由职业） | 必填，与学生状态互相独立 |
| `school` | string | 在校时学校全称必填；毕业时复用为机构 / 公司，可为空 |
| `grade_major` | string | 在校可选；毕业时清空 |
| `identity_type` | 现有字段 | 前端临时兼容：在校发 `student`，毕业发对应创作身份；最终语义和兼容迁移待后端确认 |

GET 与 PUT 成功响应的 `data.profile` 须准确返回 `student_status`、`creator_type` 和已保存的学校、年级等字段。服务端必须支持学生与任意创作身份组合，毕业时允许 `school` 为空，并同步调整校验、持久化、工作流账号同步与下游创意表单对学校必填的约束。旧数据中 `identity_type=student` 可识别在校状态，但创作身份不能推断；其他历史身份也无法可靠推断是否毕业，迁移规则待确认。后端忽略新字段时前端提示资料可能部分保存，不展示完整保存成功。

### 所在地省市联动（待后端确认）

- 新增 `province`：string，省 / 直辖市 / 地区名称，必填；`city`：string，城市名称，必填。两个值独立存储并在 GET 和 PUT 返回的 `profile` 中回显，以支持城市统计。
- 现有 `city` 可能包含“山东 · 济宁”等自由文本，不能当作新格式直接统计；后端需要迁移方案，前端会展示原值并要求用户重新选择，不自动猜测。
- 在常见选项之外，前端允许手动填写其他地区和城市。校验、统计口径、行政区变更和跨地区数据由前后端共同确认，不能假定字符串永不变化。
- 大陆省市选项基于 [Administrative-divisions-of-China](https://github.com/modood/Administrative-divisions-of-China) 的 2023 年快照，已与 [民政部 2025 年行政区划数据](https://github.com/dataxiv/data-district/tree/main/%E6%B0%91%E6%94%BF%E9%83%A8/2025)核对地级区划，并保留省直管县级单位；另补充港澳及[台湾地区县市](https://www.bjstb.gov.cn/bjtb/jtfc/bdtw/twgk/index.html)。静态数据可能过期，长期建议使用后端统一维护的地区目录。
